## Planned changes, skips, refills, backup protection (owner request)
- Planned changes (`medication.plannedChanges`): a dated future schedule and usual dose, e.g. one per taper step. Applied
  on its user day at start-up (before the first screen, so a morning tag tap already uses it) and every 5 minutes; each is
  recorded as a dated `changed` event. "Plan a change" reuses the schedule editor (`ScheduleFields`). Today shows
  "Changes Fri 23 Oct: …" in the week before; Meds shows "Change planned from …".
- Skipped doses (`dose.skipped`, `skipReason`): hold their place in the day's plan (next amount/set time moves on; the
  interval rhythm continues from the skip) but never count as taken, never change stock, and aren't the "last dose".
  Shown in the timeline, report and CSV; excluded from charts.
- Refill forecast (`logic/plans.ts`): walks the plan day by day (including planned changes) until stock can't cover a
  day; as-needed and open-ended plans use the last 30 days' use. Repeats left and script expiry on the medication.
  Today card when at/below the low-stock number, running out within "warn me N days ahead" (default 7) or script
  expiring within 30 days; Add stock (optionally uses a repeat, with undo).
- Backup files are always encrypted (AES-256-GCM) with a key built into the app (owner decision: no password). Opening a
  file, or a cloud/email preview, shows scrambled text; any copy of the app restores it with no password. The key is in
  public code, so this deters casual reading, not a determined attacker. NEVER change `BACKUP_KEY` in `logic/crypto.ts`,
  or older backups can't be restored. Plain (unencrypted) backups from before still restore.
- Automatic backups: File System Access folder (Chrome desktop / recent Android Chrome), daily when the app is open,
  keeps the last N; Today card if the browser needs permission again. Elsewhere (iPhone): "Remind me every N days".
  The folder permission is kept in the device-only `device` table (DB v3), never backed up.
- Automatic backups in the native apps (owner report: "the button does nothing"): the app WebView's folder picker
  failed straight away and the cancel was swallowed silently. The apps now use the phone's own picker through
  MedTapNative (`pickFolder`, `folderAccess`, `writeFile`, `listFiles`, `deleteFile`): Android's storage access
  framework (persisted tree permission; Android won't allow the Download folder itself, so pick a subfolder) and the
  iPhone Files picker (security-scoped bookmark). Every tap now ends with a message (saved, "No folder chosen", or the
  reason it failed), and the card shows the folder's name. Tests: `tests/autoBackup.test.ts`, plus browser runs of the
  web picker and of the app bundle with a fake native bridge.

## Tags open the Android app (owner report: "tags open the browser, not the app")
- Cause: Chrome registers NDEF_DISCOVERED for every http/https link, so a tag holding only the link goes to Chrome
  (or a chooser) even with the app's own NDEF filter. Fix: the Android app writes an Android Application Record
  (`android.com:pkg` = app.medtap.tracker) after the link record. Android then opens the app directly; iPhones and
  browsers still use the link (first record). Trade-off: on an Android phone without the app, such a tag opens the
  Play Store page for the package (not listed) instead of the website.
- Existing tags: Test this tag (in the app) reports tags without the record and offers **Update this tag**, which
  rewrites the same link plus the record (still linked). The website's tag page on Android shows "Open in the app"
  (an intent:// link to the same tag, falling back to the download page).

## Goals and forecasts (weight, waist)
- `person.goals` (one per metric: target, optional date, start value/date; synced with people).
- `logic/forecast.ts`, pure: daily series (repeats averaged) → Theil–Sen rate and level over the last 4 weeks
  (6 if sparse; needs 5 logs over 7+ days). Likely range = 1.5 × the rate's standard error (MAD scatter) plus
  any change between the window's halves beyond what the scatter explains. ETA with early/late dates (late is
  open-ended if the slow end isn't heading there; capped at 3 years), "N days sooner/later than last week"
  (same forecast on data up to a week ago), slowing (last fortnight < 60% of the one before), flat/away states,
  reached (+ drift since), milestones (5/10/15/20%, halfway, goal), pace needed for a target date with a note
  over ~1% body weight a week. Chart trend = robust line over the previous 3 weeks at each day (no lag).
- UI: Body goal cards + goal sheet (start prefilled from the trend), Today one-liner, Trends "goal forecast"
  chart (logs, trend, goal line, forecast with likely range), Help "Goals and forecasts". kg/lb and cm/in.

## Smart progression (owner: "smart predict increases in exercises to ensure we are pushing ourselves")
- `src/logic/progression.ts`. Today's target starts from the simple rule (up a step when every set hit its reps) and
  then uses the person's evidence: an RPE-aware estimated max per session (RPE 8 at 5 reps counts as 7 reps to
  failure), its robust trend (capped at +1.5%/week for planning, never below the last two sessions), and the load that
  leaves about 2 reps in reserve at the target reps (rounded to the nearest loadable step).
  - Push: more than one step (at most 2 steps or 5%) when sets felt easy (RPE ≤ 7), target reps were beaten by 2+, or
    the trend says there's room. Timed / bodyweight: +5 s or +1 rep extra.
  - Hold: on a low-readiness day (< 55), or a usual weaker day after the shot (4%+ below their level), match last time.
  - Same with a note when every set got there at RPE 9+.
  - No effort logged in the last two sessions: "Last set: as many good reps as you can, stopping 1 short" to tune.
- In a workout (Settings → "Adjust the next sets as I go", on): after a set at RPE ≤ 7 that hit its reps, the
  exercise's remaining sets go up a step; RPE 9.5+ or 2+ reps short, down a step; toast with Undo. Works when RPE is
  chosen after ticking too.
- Exercise page: Push / Hold / Aim with the reason and the usual step when it differs; "If each session goes to plan"
  (next 4 sessions, dated by how often the lift is done, starting from today's target) and the weekly trend %.
- Effort check: "Room to push" on Training (60%+ of sets in 3 weeks at RPE ≤ 7) and "progress has slowed from x% to
  y% a week" on the exercise page.
- Start a workout, repeat a session, routines and machine tags lay sets out at the smart target.
- Tests `tests/progression.test.ts` (10); browser flow: room to push, push weight, laid-out sets, auto-adjust + Undo.
- Emulator: without hardware acceleration the Android system itself crashed (DeadSystemException) shortly after
  install, so there's still no on-device result; a real phone is needed.

## Private view (a second, privacy PIN)
- **Settings → Privacy → Private view** (only with app lock on, and only in the full view): a second PIN of the same
  length. On the lock screen the main PIN opens everything; the privacy PIN opens the same-looking app in the private
  view. The mode is kept in memory only (`src/app/viewMode.ts`), so every unlock decides it again.
- **Per medicine** (its page, once a privacy PIN exists): shown as it is, under a cover name, or left out with its
  doses, tags and history. Peptides default to left out while "Leave out peptide tools" is on (MedTap).
- **How:** the data hooks in `src/app/data.ts` apply the rules (`src/logic/privateView.ts`), so every screen follows:
  - left-out medicines and their records disappear;
  - covered ones lose anything identifying (ingredients, instructions, notes, peptide setup, vials, batches);
  - the peptide tools read as off, and their screens and Help topic fall back.
- **The private view never mentions itself:** no private-view settings, no Change PIN or Turn off (that would open the
  full view next time), and no restore or automatic backups (a restore would overwrite what it leaves out).
  - Manual backups and spreadsheets made there hold only what it shows, and nothing about the privacy PIN.
  - A left-out medicine's tag says "Nothing to log".
  - Editing a covered medicine renames the cover; its real details are kept.
- **Seen without unlocking:** with a privacy PIN set, reminders use the cover name (left-out medicines just say
  "Reminder" and the time), and widgets, the watch and app shortcuts follow the private view.
- A privacy screen, not encryption: the data is still on the phone (as with the PIN itself).
- Tests `tests/private-view.test.ts`. Browser:
  - the PINs must differ;
  - the private view shows no real names, peptides or Protocol on any screen, Help or direct links;
  - the cover name is shown and editable without touching the real one;
  - the main PIN brings everything back.

## Decisions
- Working title `MedTap` (src/config.ts + vite.config.ts manifest). Change when owner confirms APP_NAME.
- **Permanent address (owner decision): https://lumenbuild.github.io/MedTap/** — no custom domain, ever. Tags are
  `https://lumenbuild.github.io/MedTap/?t=<ID>`. The workflow pins `VITE_TAG_BASE` to it and fails the build if the repo
  is renamed (Pages doesn't redirect after a rename, so every tag would break). Local/dev builds without
  `VITE_TAG_BASE` use the current address and show a "test address" warning when linking a tag.
- Dose `amount` is in the medication's unit (e.g. mg). Stock counts tablets/items and goes down by amount ÷ strength
  (shown to the user in the editor).
- Doses later than `now` don't count towards "today" (matters for backdated context notes).
- Set-times: a dose within ±60 min covers a time. Once a time's window closes unlogged, the countdown moves to the next one;
  if none remain and the day isn't complete, status is "past your latest dose time".
- Interval: countdown starts from the first dose of the user's day; before it, "No doses yet today".
- Theme preference is in localStorage (display pref only); records are IndexedDB only.
- Live data uses Dexie's built-in `liveQuery` via a tiny `useLive` hook (no extra dependency).
- Check-in scales are five large buttons (1–5) rather than sliders: easier with a thumb and can be left unanswered.
- An every-few-hours plan with a daily number has no "next dose" once complete (status Done for today).
- Not supported yet: calendar-month schedules (e.g. the 1st of each month); use every 28/30 days instead.
